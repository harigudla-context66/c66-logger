c66_logger data flow v0.4

The host package creates the logger with a tenant, an environment and the connection object its connection library returned (Postgres or ClickHouse). Each run is one row in logs.log_run, written synchronously when it starts and again when it ends. Each logged item is one row in logs.log_entry, batched by a background thread. c66-chatbot's existing logging calls arrive through Telemetry, which has the same function signatures. Nothing here looks up credentials.

once, at construction per run, synchronous every log call, buffered

What each piece is responsible for

ComponentRole
Connection libraryOutside c66_logger: c66_clients, or c66-chatbot's get_pg_conn() / get_ch_client() today. The host passes what it returns as connection=: a connection, a pool, an engine, a client or the factory itself. c66_logger never closes it.
AuditLoggerCreated by the host with target_type and connection (or a ready-made sink=), plus tenant_id and environment_id, or none and bind() one logger per tenant, all sharing one sink and writer. It checks the tables while it's being built. It holds no global state.
Telemetryc66-chatbot's nine logging helpers (log_event, log_llm_call, …) with the same signatures. A chat request becomes one run; its LLM calls, graph queries and retrieval become entries in it. Never raises.
audit.run()One logs.log_run row (record_run() writes a finished one in one call). It's inserted as Running and updated to Completed, Failed or Cancelled, with ended_at, duration_ms and error_summary. Both writes are synchronous. Entries logged inside the block get its run_id.
LogEntryOne logs.log_entry row per item. Keys that match a column set it; the rest go to metadata_json. Location, process, thread and exception are captured automatically. Levels are limited to the five the CHECK allows.
BufferedWriterQueues entries, and one daemon thread writes them in batches of 500, every 2 s, or on flush(). SyncWriter replaces it when mode="sync".
PostgresSinkPlain DB-API (psycopg2 or psycopg 3) on the caller's connection, pool, engine or factory. Writes the existing tables and never creates them. Entry inserts are idempotent. If a batch hits an FK or CHECK violation, it retries row by row so only the bad rows are rejected. Runs are upserted on run_id.
ClickHouseSinkThe same two tables as ReplacingMergeTree, on the caller's clickhouse_connect or clickhouse_driver client. Retried batches carry a dedup token, so they don't duplicate. Each run status is a new row version; read log_run with FINAL. No foreign keys.
MongoSinkTwo collections, log_entry and log_run, with the same field names as the tables. _id is log_id or run_id.
S3 / Kafka (planned)One BaseSink subclass each, implementing write_batch and write_run. to_json() gives the table-shaped JSON they'd write.
